# Type tree paths, colour, and coordinate units

## User Story

As a maintainer, I want the untyped `Vec<usize>` tree paths, `i64` colour sentinels, and unit-less `i64` coordinates left over from the early Rust port to be replaced with types that make illegal states unrepresentable, so that the two `.unwrap()` calls in `command_mode.rs` relying on an unenforced "path is never empty" convention become provably safe, and so that forgetting the `PLAIN` sentinel check, or converting cell coordinates to pixels ad hoc in more than one place, becomes harder to get wrong by construction.

## Acceptance Criteria

- A new `Path` struct is added to `state.rs`: `pub(crate) struct Path { pub(crate) ancestors: Vec<usize>, pub(crate) index: usize }`. `index` is the node's position among its siblings; `ancestors` is the path of its parent (empty when the parent is the document root). No methods are added — callers read/construct the fields directly. Non-emptiness is guaranteed structurally (there is always an `index`), not by a runtime check or fallible constructor.
- `layout.rs`'s `Label.path: Vec<usize>` becomes `Path`. The path built while recursing in `place`'s traversal is `Path { ancestors, index }` for each node, and a child's `ancestors` are its parent's `ancestors` with the parent's `index` appended.
- `Document.selected: Vec<usize>` becomes `Option<Path>`: `None` represents "nothing selected, at document root" — the state `select_parent` reaches today when popping a single-element selection (currently represented as an empty `Vec`, covered by existing tests asserting `Vec::<usize>::new()`) — and `Some(path)` represents a specific selected node.
- `command_mode.rs` is updated throughout for the `Option<Path>` type. `reduce` is the only place that inspects `Option<Path>` for commands that need a selection: it matches on `state.doc.selected` once, and the handlers that operate on a selected node (`enter_insert`, `new_sibling`, `select_parent`, `select_child`, `select_next`, `select_previous`, `edit_label`, `cycle_colour`, `cycle_siblings_colour`, `cycle_fill`, `toggle_rounded`) receive the selected `Path` directly rather than re-reading `state.doc.selected`. `reduce`'s `min_depth` guard (`state.doc.selected.len() < min_depth(command)`) becomes a computation over `Option<Path>`: `0` for `None` and `1 + path.ancestors.len()` for `Some(path)`. No `.unwrap()` on `selected` remains in `command_mode.rs` or `insert_mode.rs`, and no handler clones the selected path just to look up a node.
- Sibling navigation reads and writes `path.index` directly: `select_next`/`select_previous` become `index + 1`/`index - 1` on `path.index`, `select_parent` pops the last element of `ancestors` into `index` (or yields `None` when `ancestors` is empty), and `select_child` appends `index` to `ancestors` and sets `index` to `0`.
- `insert_mode.rs`'s `state.doc.selected.is_empty()` guard becomes a match on `state.doc.selected` that yields the `Path` without `.unwrap()`. `writer.rs`'s `with_cursor` call and `layout.rs`'s `label.path == selected` comparison are updated for `selected: Option<Path>` against `label.path: Path`.
- `state.rs`'s `at` takes `&Path`. A new `children_at(boxes: &mut Vec<Node>, ancestors: &[usize]) -> &mut Vec<Node>` returns the top-level `boxes` for an empty slice and the addressed node's `children` otherwise; `at` and every "siblings of a path" lookup (`new_sibling`, `colour_row`, `select_next`'s sibling count) go through it using `&path.ancestors`, so no parent `Path` is ever rebuilt. `colour_row` takes `&Path`.
- `grow` knows nothing about paths: `grow(siblings: &mut Vec<Node>) -> usize` appends a `PAD`-labelled default node to the given list and returns its index. Callers build the new selection from the `Path` they already hold, without converting it to a slice or concatenating: `new_sibling` selects `Path { ancestors: path.ancestors, index }` after growing `children_at(boxes, &path.ancestors)`; `new_box` with a selection grows the selected node's `children`, pushes the old `index` onto `ancestors`, and selects `Path { ancestors, index }`; `new_box` with nothing selected grows the top-level `boxes` and selects `Path { ancestors: Vec::new(), index }`. `new_box` receives the `Option<Path>` that `reduce` has already taken, like the other handlers receive their `Path`.
- `Node.colour` and `Node.fill: i64` become `Option<u8>`; the `PLAIN: i64 = -1` constant is deleted. `next_colour` changes from `fn next_colour(colour: i64) -> i64` (a `rem_euclid` trick keyed off the sentinel) to `fn next_colour(colour: Option<u8>) -> Option<u8>`, cycling `None -> Some(0) -> Some(1) -> ... -> Some(PALETTE_SIZE - 1) -> None` via explicit `match`/`if`-`else`, not modular arithmetic.
- `render.rs`'s `colour(colour: Option<u8>) -> (u8, u8, u8)` and `fill_colour(fill: Option<u8>) -> (u8, u8, u8, u8)` match on `None`/`Some(i)` instead of comparing against `PLAIN`; indexing into `PALETTE` is otherwise unchanged. Reading the real terminal foreground colour to replace the hardcoded `PLAIN_COLOUR` grey is explicitly out of scope for this spec (see below).
- `layout.rs`'s `Placement { x, y, width, height }` stays `i64` and stays in cell units — no newtype is introduced to distinguish cell units from pixel units. Instead, `render.rs` gains a single explicit cell-to-pixel conversion function that both `outline_box` and `outline_arrow` call, replacing today's scattered inline `* self.cell_width` / `* self.cell_height` multiplications that currently appear independently in each function body (`outline_box`'s `width`, `height`, `first_x`, `last_x`, `first_y`, `last_y` computations, and `outline_arrow`'s equivalent).
- All existing tests are updated to construct `Path`/`Option<Path>` literals instead of `vec![...]`/empty-`Vec`, and `Option<u8>` (`Some(n)`/`None`) literals instead of raw `i64`/`PLAIN` — no test coverage is weakened or deleted, only re-typed.
- Behaviour is unchanged: every existing selection, colour-cycling, and rendering result is identical to today, pixel-for-pixel and selection-for-selection.

## Technical Design

### Why now, and why these three together

The prior architectural cleanup (specs 054-056, see [spec 056](056-simplify-layouts-row-and-column-assignment.md)) removed the Python-migration structural smells — extra tree types, unnecessary clones, `i64` used for what are really array indices. What's left is a narrower but related problem: three places where a bare primitive type (`Vec<usize>`, `i64`, `i64`) is asked to carry a meaning ("this is a tree address," "this is a palette colour or nothing," "this is a cell coordinate, not a pixel one") that the type system doesn't enforce. All three share the same failure mode — a convention that's true everywhere *by discipline*, not by construction — so they're addressed together rather than as three separate specs.

### `Path`: structural non-emptiness, no methods

The concrete symptom motivating this was two bare `.unwrap()` calls in `command_mode.rs` (`select_next`/`select_previous`), both resting on "the path is never empty" — a fact that was true by convention but not provable by the compiler. `Path { ancestors: Vec<usize>, index: usize }` makes that fact structural: there is no way to construct a `Path` with zero elements, so the selected node's sibling index is always just `path.index`.

The guaranteed element sits at the **end** of the path, not the start, because every tree operation in the editor works on the end: sibling moves change the last index, the parent drops the last index, a child appends one. A first design of `Path { head, tail }` guaranteed the first element instead, which forced every "last index" access to branch between `tail` and `head` and every parent lookup to clone and rebuild a `Path` — more verbose than the `Vec<usize>` it replaced. With `ancestors`/`index`, the parent's address is simply the borrowed slice `&path.ancestors`.

`Path` deliberately has no methods — not even a constructor. Fields are `pub(crate)`, matching the rest of the crate's visibility convention (confirmed clean by the earlier architecture audit: only one true `pub` boundary exists today, `writer::write`). This keeps `Path` a plain data shape rather than growing an API surface speculatively; call sites that need derived facts read `ancestors`/`index` directly, and sibling lookups go through the free function `children_at` in `state.rs`, which works on the `&[usize]` slice rather than on `Path`.

### Resolving "is something selected?" once

`selected: Option<Path>` must not turn into an `.unwrap()` at the top of every command handler: that would swap the two convention-based unwraps this spec removes for a dozen new ones. `reduce` already guards commands that need a selection with `min_depth`; it is also where `Option<Path>` gets matched, so handlers take the `Path` as a parameter and the type system — not the guard — proves a selection exists.

### `selected`'s legitimate empty state: `Option<Path>`, not `Path`

The first pass at this design assumed `selected` should reuse the same non-empty `Path` type as `Label.path`. That's wrong: `select_parent` legitimately pops a single-element selection down to *nothing selected, at document root* — an empty `Vec<usize>` today, asserted directly by existing tests. A `Label.path`, by contrast, always names an actual node and is never empty. These are different concepts that happened to share a type by accident of both being `Vec<usize>`. `Document.selected: Option<Path>` keeps `Path` non-empty everywhere it's used for "an address of a real node" (`Label.path`), while making "nothing is selected" an explicit, typed state (`None`) instead of an empty-vec convention that the non-empty `Path` type would otherwise make unrepresentable in the one place it's actually needed.

### Colour: `Option<u8>` over a `Colour` enum or a prepended palette entry

`Node.colour`/`fill: i64` used `-1` (`PLAIN`) as a sentinel alongside small non-negative palette indices. `Option<u8>` was chosen over a dedicated `Colour` enum because the only two states that exist are "an index into `PALETTE`" and "nothing" — an enum would just be `Option` with extra ceremony. It was also chosen over prepending the current terminal foreground colour as palette index 0 (raised and considered during design): that would require a live terminal query (e.g. an OSC 10 round-trip) to read the real foreground colour, which is a new I/O capability out of proportion to a type-safety cleanup, and `fill`'s "plain" state isn't a colour at all today (it renders fully transparent, not grey), so `colour` and `fill` don't actually share "plain" semantics that a shared prepended palette entry could unify. Reading the real terminal foreground colour remains a candidate for a future, separate spec; this one keeps `PLAIN_COLOUR`'s hardcoded grey as the `None` rendering, unchanged from today.

### Coordinates: no newtype, one conversion choke point

`Placement`'s `i64` fields (cell units, produced by `layout.rs`) and `Canvas`'s `i64` fields (pixel units, consumed by `render.rs`) were flagged as indistinguishable at the type level. Rather than introduce `Cell(i64)`/`Pixel(i64)` newtypes — which would ripple through every arithmetic site in both files for a unit distinction only one boundary actually cares about — the fix is structural: `Placement` and `Canvas` already are separate types, so keeping cell values only in `Placement`-shaped data and pixel values only in `Canvas`-shaped data is sufficient separation, *provided* the conversion between them happens in exactly one place. Today it doesn't: `outline_box` computes `width`, `height`, `first_x`, `last_x`, `first_y`, `last_y` as six independent `* self.cell_width` / `* self.cell_height` expressions, and `outline_arrow` repeats the pattern. This spec collapses both into calls to one conversion function, so a future unit mistake has exactly one place to be wrong instead of two (and growing).
