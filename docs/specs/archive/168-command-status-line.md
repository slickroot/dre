# Command Status Line

Marouane is editing a diagram in dre. He presses `b` to create a new box. At the bottom-center of the screen, on the same row as the footer, he sees `["b" Create New Box 20ms]` appear — confirming exactly which command just ran and how long it took. He presses another key, and the line updates to reflect that new command. Before he's pressed anything, that space is simply empty.

## Acceptance Criteria

- The command-status line sits at the bottom-center of the screen, on the same row as the footer.
- Before any command has been executed, the space is empty.
- After every command — not just box actions, but any dispatched command including selection/navigation — the line updates to show the one just executed.
- Only the most recent command is shown (no history/log).
- Format is exactly: `["<key>" <Human-Readable Command Name> <duration>ms]`

## Technical Design

The control loop (`DreController::run` in `src/editor/controller/mod.rs`) already has precedent for a similar problem: the LED flash (spec 166) mutates a transient render-timing field on `State` from the imperative shell, outside the pure `reduce`/`Action` pipeline. The command status line follows the same split — a pure lookup for *what* to show, and impure timing in the controller for *how long it took* — but, unlike the LED flash, its value persists across frames instead of being reset every `reduce()` call.

- **A new `CommandStatus` struct** in `src/state/mod.rs`: `{ key: String, name: &'static str, duration_ms: u128 }`. `State` gets `command_status: Option<CommandStatus>`, defaulting to `None` (the empty space before any command has run). `reduce()` never resets this field — it only changes when a new command overwrites it.
- **`state::command_label(state: &State, key: &str) -> Option<(String, &'static str)>`**, a new pure, crate-visible function that mirrors `input::parse`'s binding lookup (same matcher precedence) but returns the pair the status line needs: the key text to display, and the matched `KeyBinding`'s existing `description` field verbatim (no rewording — `description` now serves both the README table and this status line). For the `Printable` matcher in Insert mode, it returns the literal typed character instead of the binding's `"Printable"` placeholder; for every other matcher it returns `binding.display`, same as today.
  - Returns `None` (no status update) when: `state.mode()` is `Mode::NamePrompt`, or the resolved action is `Action::Immediate(ImmediateCommand::Digit(_))`, `CancelCount`, or `Interrupt`. Every other action in Command and Insert mode — including non-undoable moves like `SelectNext`/`SelectParent`, and `OpenNamePrompt` itself — counts. No new taxonomy on `Action`; this is a direct, explicit check alongside the existing `input::parse` call.
- **`state::set_command_status(state: State, key: String, name: &'static str, duration: Duration) -> State`**, a small pure setter (same shape as `state::flash`) that stores `CommandStatus { key, name, duration_ms: duration.as_millis() }` on a state copy. This is the only place `command_status` is ever set.
- **`DreController::run`** changes: for a real keystroke (not the resize key), it first calls `state::command_label(&state, key)`. If that returns `Some((key, name))`, the controller starts an `Instant::now()` timer, calls `self.reducer.reduce(state, key)` and `self.executor.execute(effects, &next)` as today, then **renders `next` immediately** (so the doc/selection/mode change is visible right away, still carrying the *previous* status text), stops the timer, and calls `state::set_command_status(next, key, name, elapsed)` to produce the state assigned back into the loop variable. That state is what the loop's normal top-of-iteration `render` call shows on the very next pass — the status line update lands one render call later than the rest of the frame, the same lag pattern the LED flash already relies on. When `command_label` returns `None` (digits, cancel, interrupt, name prompt), the controller behaves exactly as it does today — no extra render, no timing, `command_status` simply carries over unchanged.
- **`State::command_status(&self) -> Option<CommandStatus>`**, a new model-getter parallel to `State::footer()`, just returning a clone of the field — mode-independent, so it keeps showing the last real command's status even while the name prompt is open.
- **`view::command_status(status: &Option<CommandStatus>) -> Vec<Placement<'static>>`** in `src/view.rs`: returns an empty `Vec` when `None` (empty space, per the acceptance criteria), or a single `Label` placement with text `format!("[\"{}\" {} {}ms]", status.key, status.name, status.duration_ms)` when `Some`.
- **A new `align_center` function** in `src/view.rs`, parallel to the existing `align_right`, to center the command-status placements horizontally within the `foot` area.
- **`view::editor`** adds one more entry to the `Scene`: `(foot, align_center(command_status(&state.command_status()), foot))`, alongside the existing `(foot, footer)` entry — the renderer already paints multiple placement groups against the same `Area` in sequence (see `TerminalRenderer::frame`), so no changes are needed there. This keeps the command status line a fully separate component from `FooterModel`/`footer()`, sharing only the row.

No changes are needed to `src/state/command.rs`'s ~1500 lines of command handlers, or to `input::parse` itself — `command_label` does its own read-only pass over the same `KEYMAP` table.
